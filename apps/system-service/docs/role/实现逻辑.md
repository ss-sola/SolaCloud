# 实现逻辑

## 分层职责

- `controller`：接收 query 和 body，并统一返回 `ResponseUtil.success(...)`
- `service`：承载角色 CRUD、权限绑定替换、运行态聚合与日志写入
- `entity`：声明角色主表与角色权限关系表
- `form`：通过 `class-validator` 校验保存、查询和运行态参数

## 核心流程

### 1. 查询流程

- `listItems(query)`：按 `isEnabled` 下推数据库过滤，再按 `keyword` 在返回记录上补充筛选
- `listOptions()`：只查询启用角色，返回 `code/name` 最小字段，供账号角色绑定等跨模块选择场景使用；接口通过 `@RequireAnyPermissions(...)` 允许角色管理权限或账号管理权限访问
- `getItem(id)`：返回角色基础信息以及关联的 `permissionCodes`
- `getRuntimeByRoleCode(roleCode)`：基于角色编码聚合可用菜单树；权限码仅在服务内部用于菜单过滤，不作为运行态响应字段返回

### 2. 写入流程

- `createItem(payload)`：
  1. 校验角色编码唯一性
  2. 将 `permissionCodes` 去重、去空白
  3. 校验权限码存在且启用，并映射为 `permissionIds`
  4. 保存角色主表
  5. 重建角色权限关系表
  6. 清理历史遗留的角色菜单、角色用户关系
  7. 写入操作日志
- `updateItem(id, payload)`：与创建流程相同，但会先校验记录存在
- `removeItem(id)`：删除主表前清理角色权限关系，并同步清理历史遗留的角色菜单、角色用户关系
- 角色新增、更新、删除后都会调用 `RuntimePermissionService.invalidateAll()`，避免账号继续使用旧角色权限缓存

### 3. 权限绑定规则

- `replaceRelations(roleId, payload)` 每次更新都会先清空旧关系，再按去重后的权限 ID 重建 `sys_role_permission`
- `permissionCodes` 是角色权限绑定的唯一对外输入；服务端会映射成 `permissionIds`
- 当前角色模块不再直接维护菜单绑定与用户绑定

### 4. 运行态聚合规则

- 角色必须存在且处于启用状态
- 仅在服务内部读取当前角色已绑定且仍处于启用状态的权限码
- 运行态菜单基于“角色权限码”与“菜单 permissionCodes”做匹配
- 若子菜单命中权限，父节点会自动补齐，最终由 `MenuRouteUtil.buildTree(...)` 统一组装树
- 未配置 `permissionCodes` 的启用菜单视为公共节点，可直接进入运行态菜单树
- 运行态响应中的菜单树会移除 `permissionCodes` 字段，仅保留前端渲染所需菜单信息

### 5. 默认角色授权

- 初始化数据见 `sql/init_data.sql`。角色写入 `sys_role`，对应的权限绑定写入 `sys_role_permission`。
