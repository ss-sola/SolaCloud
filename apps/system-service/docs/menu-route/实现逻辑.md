# 实现逻辑

## 分层职责

- `controller`：接收 query 参数与请求体，调用 service，并通过 `ResponseUtil.success(...)` 返回响应。
- `service`：承载菜单列表、树构建、创建、更新、删除、批量启停、排序调整与规则校验逻辑。
- `entity`：声明 `sys_menu_route` 表结构。
- `form`：使用 `class-validator` 定义查询、创建和更新参数。
- `util`：承载无状态辅助逻辑，包括树构建、权限码归一化与种子结构转换。

## 核心流程

### 1. 列表与树查询

- `listItems(query)`：将 `parentId`、`isEnabled`、`keyword` 尽量下推到 repository 查询。
- `keyword` 只对 `code / name / path` 生成 `ILike` 条件，不再匹配 `routeName`。
- `listTree(query)`：在 `listItems(query)` 基础上通过 `MenuRouteUtil.buildTree(...)` 组装树结构。
- `RuntimePermissionService` 与 `RoleService` 输出运行时菜单树时，会继续复用树构建链路，但返回字段统一为 `path / component / icon / permissionCodes / meta`；前端再根据 `meta.routeRoot` 解析一级域。

### 2. 创建与更新流程

- `createItem(payload)`：
  1. 校验 `code` 是否唯一。
  2. 校验 `parentId` 是否存在且合法。
  3. 校验 `permissionCodes` 是否都存在且启用。
  4. 调用 `toEntityPayload(...)` 做字段归一化。
  5. 保存并写入操作日志。
- `updateItem(id, payload)`：
  1. 查询当前菜单是否存在。
  2. 校验父节点是否合法。
  3. 校验权限码是否合法。
  4. 合并原记录与归一化字段。
  5. 继续保留原有 `code`，不允许通过更新接口改写菜单编码。
- `toEntityPayload(...)` 统一归一化 `name / path / component / icon / permissionCodes / meta`，不再处理 `routeName`。

### 3. 批量维护流程

- `batchUpdateStatus(payload)`：校验 `ids` 非空且全部存在后，批量更新启停状态，并写入操作日志。
- `reorderItems(payload)`：按提交的 `id + sort` 更新排序值，返回重新按排序升序排列的结果，并写入操作日志。

### 4. 删除流程

- `removeItem(id)`：查询目标菜单，校验不存在子节点后执行删除，并写入操作日志。

### 5. 默认菜单初始化与真实数据同步

- 当前菜单与菜单权限关系的初始数据由 `sql/init_data.sql` 提供，分别写入 `sys_menu_route` 与 `sys_menu_route_permission`。
- `apps/system-service/scripts/sync-menu-route-data.cjs` 适用于旧版菜单表结构。

### 6. 运行态缓存联动

- 菜单新增、更新、批量启停、排序调整、删除后，都会调用 `RuntimePermissionService.invalidateAll()` 清空账号运行态权限缓存，确保管理台菜单与权限判断读取最新菜单配置。
