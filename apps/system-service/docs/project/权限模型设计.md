# 权限模型设计

## 设计目标

system-service 的权限模型以权限码为唯一授权单位，角色只负责聚合权限码，菜单、接口和前端交互都消费同一份权限码。

目标是避免以下问题：

- 用户能看到菜单，但页面首屏接口无权限。
- 用户能看到按钮，但点击后接口拒绝。
- 页面为了使用其他模块数据，被迫授予完整管理权限。
- 一个粗粒度 `manage` 权限同时代表查看、创建、修改、删除和跨模块引用。

## 权限分层

### 1. 菜单入口权限

菜单入口权限用于判断用户能否看到并进入页面。

示例：

```ts
system: account: view;
```

菜单上的 `permissionCodes` 应优先绑定页面入口权限。用户拥有入口权限时，页面首屏所需的基础查询接口也必须可用。

### 2. 页面基础查询权限

页面基础查询权限用于列表、详情、总览等首屏必需接口。它通常与菜单入口权限一致。

示例：

```ts
@RequirePermissions(SYSTEM_PERMISSION_CODES.accountView)
@Get()
async listItems() {}
```

这样可以保证“菜单可见”和“页面可加载”一致。

### 3. 动作权限

动作权限用于新增、编辑、删除、重置密码、绑定角色等具体操作。

示例：

```ts
system:account:create
system:account:update
system:account:delete
system:account:password-reset
system:account:role-save
```

后端接口必须按动作权限拦截；前端按钮也应基于运行态权限码隐藏或禁用。

### 4. 跨模块选择项权限

页面需要引用其他模块资源做下拉、选择、绑定时，不直接复用完整管理列表接口。

标准做法是由资源归属模块提供轻量 `options` / `lookup` 接口。

例如账号页绑定角色：

```http
GET /api/system/roles/options
```

该接口归属 role 模块，只返回绑定需要的最小字段：

```json
[
  {
    "code": "admin",
    "name": "管理员"
  }
]
```

它不等价于完整角色管理列表：

```http
GET /api/system/roles
```

完整列表服务角色管理页，选择项接口服务其他业务场景。

## 任一权限规则

跨模块选择项接口经常需要允许多个业务入口访问。

例如角色选项接口应允许以下任一权限访问：

```ts
@RequireAnyPermissions(
  SYSTEM_PERMISSION_CODES.roleManage,
  SYSTEM_PERMISSION_CODES.accountManage,
)
@Get('options')
async listOptions() {}
```

含义：

- 有角色管理权限的用户，可以在角色模块内读取角色选项。
- 有账号管理权限的用户，可以在账号页绑定角色时读取角色选项。
- 没有任一权限的用户不能读取。

## 接口归属规则

接口归属看资源所有权，不看当前页面位置。

- 角色选项归 role 模块：`GET /api/system/roles/options`
- 账号角色保存归 account 模块：`PUT /api/system/accounts/roles?id=...`
- 角色创建、编辑、删除归 role 模块完整管理接口

不要为每个调用方重复创建：

```http
GET /api/system/accounts/role-options
GET /api/system/notifications/role-options
GET /api/system/audit/role-options
```

这会让角色读取规则散落到多个模块。

## 前端消费规则

运行态权限接口应返回当前账号的权限码集合。前端页面基于权限码控制交互展示，后端 guard 仍然是最终授权边界。

示例：

```js
if (hasPermission('system:account:role-save')) {
  renderRoleBindingButton();
}
```

前端控制只改善体验，不能替代后端权限校验。

## 命名建议

常用轻量选择接口命名：

- `GET /roles/options`
- `GET /roles/lookup`
- `GET /roles/assignable`

后台管理系统中优先使用 `options`，语义直接，适合表单和绑定场景。

## 权限分组规则

权限码 `code` 是稳定授权标识，用于角色绑定、菜单匹配和接口 guard 校验，不因页面展示分组变化而改名。

`groupKey` 只用于权限管理页的业务分组展示和筛选。默认权限码按业务类型分组：

- `platform`：平台入口类权限
- `resource`：字典、菜单、系统参数、通知公告、编号规则等基础资源权限
- `identity`：账号、角色、权限码等身份权限类权限
- `audit`：登录日志、操作日志等审计查询权限

## 当前落地策略

当前 system-service 仍保留现有粗粒度管理权限码，例如：

```ts
system: account: manage;
system: role: manage;
```

在此基础上先落地跨模块选择项接口和任一权限规则。后续需要更细粒度控制时，再将 `manage` 逐步拆成 `view/create/update/delete` 等动作权限。
