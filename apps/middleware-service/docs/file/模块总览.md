# 模块总览

文件上传模块现在只提供一套上传协议：`check / upload / merge` 三接口的分片上传与合并流程。

## 当前实现

- `POST /file/upload/check` 接收前端按“前端会话 id + sourceHash”计算出的 `fileId`，并继续接收 `totalSize / chunkSize / chunkCount / sourceHash` 作为校验与续传参数；服务端校验 `fileId` 与 `sourceHash` 的对应关系，检查是否已有可复用的活动上传会话，并返回服务端真实已落盘的 `uploadedChunkIndexes`。
- `POST /file/upload` 只负责上传单个分片；客户端使用 `fileId` 标识上传会话，服务端按会话的 `uploadId` 将分片落到非公开临时目录。
- `POST /file/upload/merge` 会在全部分片齐备后接收 `fileHash` 与最终保存元数据（`originalName / mimeType / scene / businessType / isTemporary`），顺序合并分片，对合并出的正式文件重新计算 `SHA-256`，与前端传入的 `fileHash` 一致时才生成最终文件元数据。
- 上传过程中的中间态不再由接口直接信任数据库计数，而是由磁盘分片快照与 Redis 共同驱动：
  - Redis 保存当前会话元信息、已上传分片索引和合并锁。
  - 磁盘分片目录仍是可对账的事实依据。
  - `middleware_file_upload_session` 保留为审计与过期清理依赖的数据源。
- 正式文件仍写入本地磁盘并保存到 `middleware_file_item`；数据库中只保存相对 `storagePath`，对外返回时统一组装完整 `url` / `previewUrl`。

## 职责边界

- `controller`：负责 `check / upload / merge / list / detail / remove` 的协议转换、参数清洗与响应包装。
- `FileUploadSessionService`：负责上传会话创建、复用、分片上传、进度对账、合并校验和过期上传清理。
- `FileUploadRedisService`：负责 Redis key 构造、会话快照读写、分片索引保存和合并互斥锁。
- `FileStorageService`：负责分片落盘、分片存在性判断、已上传分片扫描、顺序合并和物理文件删除。
- `FileService`：负责正式文件列表、详情、删除和过期正式临时文件清理。
- `FileUploadUtil`：提供布尔值/字符串归一化、百分比计算与安全路径辅助。

## 路径与存储约束

- 正式文件元数据只保存相对 `storagePath`。
- 上传会话只保存相对 `chunkDirPath`。
- 分片目录必须位于非公开目录下，避免未合并分片被静态暴露。
- 同一前端会话 id 下，同一源文件只允许存在一条活动上传会话；如果分片配置冲突，`check` 会直接返回冲突错误。
