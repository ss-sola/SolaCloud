# 实现逻辑

## 队列连接

`TaskQueueService` 读取 `QueueRedisUrl` 创建 Redis 连接，账号、密码和 DB 由 Redis URL 表达。服务按任务类型创建 BullMQ Queue，并统一配置 Redis key 前缀、重试次数和退避策略。

当前任务定义包含：

- `upload-cleanup`：队列名称为 `middleware-task-upload-cleanup`。

## Worker 生命周期

`TaskWorkerService` 实现 `AfterApplicationBootstrap`，在应用初始化完成后为每种任务类型启动对应 Worker。当前 `upload-cleanup` Worker 只监听 `middleware-task-upload-cleanup` 队列，处理逻辑直接调用：

- `FileService.cleanupExpiredTemporaryFiles()`：清理正式临时文件。
- `FileUploadSessionService.cleanupExpiredUploadSessions()`：清理未完成上传会话和分片目录。

应用关闭时先关闭所有 Worker，再关闭 Queue 和 Redis 连接。

入队时将当前 trace 的传播头随任务保存。Worker 开始处理时创建消费 span，并将处理结果或异常交还 BullMQ。附件描述任务以队列、job ID、创建时间及任务名派生稳定操作标识，RAG 用它为文件描述回写生成独立的幂等键。相同任务重投可识别已提交的描述写入；若模型生成了不同描述，回写报告冲突，Worker 将此次处理标记为失败。

## 定时清理

内置任务名为 `upload-cleanup`，cron 表达式由 `QueueCleanupCron` 控制，默认每小时执行一次。repeatable job 会注册到 `middleware-task-upload-cleanup` 队列。

## 队列面板

启用 `BullBoardEnabled` 后，Bull Board 会注册 `TaskQueueService.getQueues()` 返回的全部队列，因此不同任务类型会在面板中显示为独立队列。
