# SolaCloud 网关服务实施方案

## 背景与目标

NestCloudWeb 目前在 Vite 中分别代理到 system-service、middleware-service 和 rag-service。SolaCloud 增加独立的 `apps/gateway-service`，为浏览器提供同源业务 API 入口。现有登录、权限、文件及聊天协议直接沿用。NestCloud 继续提供配置和实例发现。业务服务间的调用继续通过 SDK 和私网地址完成。

本方案以现有管理前端为首批客户端，假设部署入口负责 TLS，网关可访问业务实例注册的私网 `host:port`。建议网关使用 3100 端口，本地使用固定上游，生产使用注册中心发现实例。

## 入口与路由

浏览器访问同一域名下的前端和 `/api`。本地由 Vite 将 `/api` 统一代理到 `http://127.0.0.1:3100`，生产由部署入口将 `/api` 交给网关，再处理前端 SPA 回退。网关以 HTTP 方法和路径白名单匹配请求，上游收到原路径及查询串。

| 浏览器侧路径 | 上游 | 首版规则 |
| --- | --- | --- |
| `/api/system/...` | `system-service` | 按前端实际使用的认证、系统管理和运行时接口登记方法与路径 |
| `/api/file/...` | `middleware-service` | 开放上传检查、分片、合并、查询、删除和文件树等前端已使用的端点 |
| `/api/knowledge/...`、`/api/chat/...` | `rag-service` | 登记知识库和聊天接口，`POST /api/chat/send` 使用流式响应策略 |
| `/public/uploads/...` | 文件访问域名 → `middleware-service` | 独立文件 origin 承载 `url`、`previewUrl` 和 ZIP 解压预览，按现有预览客户端配置跨域读取 |
| `/api/rag/...`、`/api/task/...`、`/api/file/batch-detail`、`PUT /api/file/description` | 私网服务 | 附件回调、任务和内部文件调用通过各服务的私网地址走现有 SDK |

控制面和 Bull Board 通过各自的运维入口访问。白名单按路径段匹配，限制参数段格式。对非规范路径返回 `400`，对未登记的请求返回 `404`。验收时覆盖大小写、尾斜杠、编码路径和控制器继承的通用 CRUD 路由，确保网关与上游对公开端点的解释一致。

登录及会话管理仍由 `system-service` 处理。网关向上游透传 `Cookie` 和业务需要的凭证，并逐条转发响应 `Set-Cookie`。各业务服务继续保有会话、权限及资源归属校验。发布前核对每条公开路由的访问规则，尤其是当前文件控制器的上传、删除和查询，以及 RAG 知识库读写。对前端受保护入口，在下游补齐缺失的登录及资源授权校验后再启用路由。参与共享会话的业务服务使用相同的 Cookie 配置、签名密钥和会话 Redis。在生产 TLS 入口验证 `Secure` Cookie 的签发和清除。

## 实现设计

### 网关应用与 SDK

- 新建 `apps/gateway-service`，沿用 NestJS、SDK `bootstrap`、自动扫描、`getConfig`、`ConfigKey`、配置校验及 Logger。接入根目录 `pnpm start:gateway`，由工作区发现构建、lint、测试和类型检查。
- 在 `AppModule` 组织启动配置。路由服务负责匹配，实例解析服务负责选址，转发服务负责流生命周期，健康检查控制器负责探针。
- SDK 启动当前会读取 `SessionSecret` 并装载会话中间件。为 SDK 增加可选启动参数，由网关显式关闭 Session 和请求体解析，默认值沿用 SDK 当前行为。网关专用的转发层处理原始 HTTP 流，业务代码继续通过 `RemoteClientBase` 发起 RPC。
- 以网关应用代码内的白名单发布开放端点。`validate.config.ts` 和 `.env.example` 定义端口、上游模式、静态地址、注册同步周期、快照有效期、连接和流超时。运行参数按部署管理，首版路由随应用发布。

### 发现、负载均衡与降级

- 静态模式为三个服务分别配置固定地址，本地示例使用 `3200`、`3300`、`3400`。注册模式通过 `RegistryUrl` 复用 SDK 的注册中心认证和实例缓存，三个上游以 `NodeEnv=production` 启用现有注册。现有 SDK 的同步依附于注册流程，补一个只发现的模式，将周期同步与网关自身注册解耦，并暴露最近一次同步成功时间。`ControlPlaneToken` 只用于控制面请求。
- 注册模式以已允许的服务名查找实例，按服务轮询，在最近的有效快照及实例租约内选址。使用实例私网 `host:port` 和原请求路径，避免将可能指向统一入口的 `baseUrl` 作为网关上游。生产配置需验证上游直连可达，并给浏览器和网关分别配置网络边界。
- 缓存按服务名保存实例，周期同步成功时整表替换，空结果也生效。建议沿用 15 秒轮询间隔，失败时最多使用距上次同步成功 45 秒的快照，并按控制面租约阈值过滤过期实例。运维可滚动重启网关触发立即同步。实例摘除后在下次同步生效，控制面恢复后自动恢复发现。无有效实例返回 `503`，连接或转发失败返回 `502`，等待上游超时返回 `504`。首版每次请求只尝试一次上游。
- `GET /health/live` 检查网关进程，`GET /health/ready` 检查路由配置和注册模式的快照是否有效。单个业务服务失效时由该服务的路由返回 `503`。探针供部署入口与运维访问。

### HTTP 转发与可观测性

- 优先使用 Node `http` / `https` 流和连接池。透传业务响应状态、内容类型、正文及必要头。按代理规则移除逐跳头，在可信入口边界重建转发头，并配置 `system-service` 只信任指定代理，用实际客户端地址记登录日志。接好 SDK 的入站、出站 span 和 `x-trace-id`。只记录路由、上游服务和实例、状态、耗时与失败类型等运维字段。
- `POST /api/chat/send` 在网关和部署入口均关闭响应缓冲。收到上游响应头即写出，事件逐段转发，使用单独的流空闲超时。客户端取消时释放代理及上游连接，已开始输出的流发生错误时结束该流。
- 分片上传保留 multipart 边界和字节流，限制单次请求体大小时计入 multipart 开销，避免低于下游允许的分片大小。文件域名保留 `Range`、`206`、`Content-Range` 和下载相关头。通过 `UploadPublicBaseUrl` 配置完整文件访问地址，检查普通文件和 ZIP 预览均返回该地址下的 URL。同步验证 RAG Worker 可访问其接收到的文件 URL。
- `middleware-service` 当前把分片、合并产物和解压文件写到本地磁盘。首版文件路由使用单实例部署。共享分片、正式文件和解压目录在各实例间验证通过后，再为文件路由开启多实例轮询。

## 实施、验收与回滚

1. 完成网关骨架和静态路由，加入 SDK 兼容启动选项。用本地可控上游测试路由白名单、方法和查询串以及错误码，再切本地 Vite 验证登录和菜单。
2. 接入只发现模式、轮询、摘除、快照过期及探针。测试注册中心启动顺序、暂时中断、空快照和恢复。确认公开入口域名不会被选为上游。
3. 接入 SSE、分片上传和独立文件域名。验收登录及退出 Cookie、管理访问、登录失效、越权拒绝、断点续传和合并、文件与 ZIP 预览、Range 下载、聊天首包及取消、附件回调和跨服务 trace。
4. 在测试环境验证一遍生产拓扑和代理配置。生产按环境或流量灰度切换 `/api`，观察网关生成的 `502`、`503`、`504`、响应耗时和 SSE 首包。回滚时将入口切回原业务路由，沿用原访问边界，并验证已发出的文件 URL 和登录状态。正式实现通过 `pnpm lint`、`pnpm test`、`pnpm tsgo` 和 `pnpm build` 后更新项目部署文档、网关模块文档和相关接口清单，按仓库约定同步新增接口到 Apifox。
