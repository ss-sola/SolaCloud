# 架构总览

## 1. 项目组成

当前仓库是一个以 `apps/*` 为边界的多应用工作区，通过 `pnpm-workspace.yaml` 管理后端与管理前端。

- `web/NestCloudWeb` 负责业务管理前端。
- `apps/gateway-service` 接收浏览器直接发出的 API 请求，通过明确的路由白名单转发到业务服务，支持静态地址和注册中心发现。
- `apps/system-service`：系统管理服务，承载前后台统一账号主体、认证、权限、字典、菜单路由等能力。
- `apps/middleware-service`：中间件服务，承载文件上传与 BullMQ 异步/定时任务能力。
- `apps/rag-service`：RAG 检索增强生成服务，支持文档知识库管理、向量检索、LLM 聊天流式输出。

## 2. 关键职责边界

### NestCloud-Sdk

`../NestCloud-Sdk` 不是业务服务，而是共享包。其他服务应优先复用这里的公共能力，而不是各自重复实现。

当前可确认的共享能力包括：

- 配置中心接入：`../NestCloud-Sdk/src/config-center/index.ts`
- 注册中心客户端：`../NestCloud-Sdk/src/client/registry-client.service.ts`
- 日志实现：`../NestCloud-Sdk/src/logger/logger.service.ts`
- TypeORM 接入装饰器：`../NestCloud-Sdk/src/database/enable-typeorm.decorator.ts`

### NestCloud

`../NestCloud` 负责两类基础设施能力：

- 配置文件版本管理、发布、拉取
- 服务注册、发现、心跳与审计

配置中心服务端实现入口：

- `../NestCloud/src/config-center/service/config-file.service.ts`
- `../NestCloud/src/registry-center/registry.service.ts`

### system-service

`apps/system-service` 负责系统管理能力，并以 `account` 作为前后台统一登录与用户主体：

- 账号与认证：统一维护 `sys_account`、登录态、密码安全状态和当前账号输出
- 角色与权限：通过 `sys_account_role`、角色权限码和运行时权限聚合控制访问边界
- 字典管理：命名空间查询、字典项维护、批量导入
- 菜单路由管理：树查询、增删改查、启停排序、权限码绑定
- 当前管理台左侧导航实际消费 `menu-route` 树数据，菜单维护后会直接影响该界面导航

当前接口约束：

- 资源标识与查询条件统一通过 query 参数传递，不使用 RESTful 路径参数
- controller 层统一通过 form 对象 + class-validator 校验 query 参数

核心入口：

- `apps/system-service/src/modules/account/controller/auth.controller.ts`
- `apps/system-service/src/modules/account/controller/account.controller.ts`
- `apps/system-service/src/modules/account/service/runtime-permission.service.ts`
- `apps/system-service/src/modules/dictionary/controller/dictionary.controller.ts`
- `apps/system-service/src/modules/menu-route/controller/menu-route.controller.ts`

### middleware-service

`apps/middleware-service` 负责可复用的中间件业务能力，首版提供：

- 文件上传：本地磁盘存储、上传元数据管理、列表查询、详情查询、删除与临时文件清理入口
- 定时任务：基于 BullMQ 和 Redis 的任务入队、状态查询、按任务类型拆分的 Queue/Worker 生命周期和上传临时文件清理 repeatable job

核心入口：

- `apps/middleware-service/src/modules/file/controller/file.controller.ts`
- `apps/middleware-service/src/modules/file/service/file.service.ts`
- `apps/middleware-service/src/modules/task/controller/task.controller.ts`
- `apps/middleware-service/src/modules/task/service/task-queue.service.ts`
- `apps/middleware-service/src/modules/task/service/task-worker.service.ts`

### rag-service

`apps/rag-service` 负责 RAG（检索增强生成）能力，支撑智能问答与文档检索。

核心能力：

- **知识库管理**：文档上传、解析、分片、向量化存储（pgvector）
- **聊天服务**：多轮对话、流式 SSE 输出、来源引用（chunkId/documentId/fileId）
- **配置服务**：LLM/Embedding 模型配置管理，支持通过配置中心切换模型

核心入口：

- `apps/rag-service/src/modules/knowledge/controller/knowledge.controller.ts`
- `apps/rag-service/src/modules/knowledge/service/knowledge.service.ts`
- `apps/rag-service/src/modules/chat/controller/chat.controller.ts`
- `apps/rag-service/src/modules/chat/service/chat.service.ts`
- `apps/rag-service/src/modules/chat/service/chat-retrieval.service.ts`

## 3. 运行关系

### 浏览器请求

管理前端直接访问网关的 `/api`，由网关向三个业务服务转发。网关允许配置中的前端来源跨域发送带 Cookie 的请求。登录会话和资源授权由业务服务处理。文件访问通过独立域名，附件回调和其他服务间 RPC 通过私网地址访问。[网关模块](../../apps/gateway-service/docs/网关/README.md)

### 配置流

1. 服务启动时，通过 `NestCloud-Sdk` 的配置中心能力加载本地配置。
2. 若启用了配置中心，服务会从 `NestCloud` 拉取远程配置。
3. 远程配置与本地开发配置合并后，统一通过 `getConfig` 暴露给业务代码。

### 注册流

1. 业务服务启动后，由注册中心客户端向 `NestCloud` 注册实例。
2. 客户端定时发送心跳，并定时同步服务实例列表到本地缓存。
3. 业务服务需要做服务发现时，从本地缓存读取可用实例。

## 4. 刻意的架构取舍

### 自动扫描注册

当前项目刻意不在业务 `AppModule` 中显式注册 controller 与 provider，而是通过 `../NestCloud-Sdk/src/register/index.ts` 中的自动扫描机制，在启动阶段按 `dist/**/*.js` 模式导入并分类注册。这是当前运行时装配模型的一部分，不是待消除的历史问题。

### NestCloud-Sdk 统一基础设施内核

`NestCloud-Sdk` 被刻意设计为统一基础设施内核，而不是轻量工具包。启动、配置中心接入、注册中心客户端、日志、数据库接入、远程调用等跨服务基础能力都统一沉淀在这里，其他服务默认依赖该层完成基础设施接入。

### NestCloud 简化控制面

`NestCloud` 被刻意设计为简化版控制面，统一承载配置中心与注册中心能力。这一实现参考了 Nacos 的一体化思路，目的是在当前项目规模下用较低复杂度支撑配置拉取、服务注册、发现与心跳续约。

## 5. 文档维护原则

- 项目级职责、交互流程、运行方式统一维护在 `/docs/project`。
- 服务私有模块说明维护在各自 `apps/<service>/docs/<模块>/`。
- 公共能力文档维护在 `../NestCloud-Sdk/docs/<能力>/`。
- 架构发生变化时，必须同步更新这里的对应文档。
