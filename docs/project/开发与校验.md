# 开发与校验

## 1. 工作区说明

根工作区通过 `pnpm-workspace.yaml` 维护 `apps/*` 子项目，并统一暴露常用脚本。

当前已确认的有效子项目：

- `apps/system-service`
- `apps/middleware-service`
- `apps/rag-service`
- `web/NestCloudWeb`

## 2. 常用根脚本

来源：`package.json`

- `pnpm build`：构建三个业务服务与管理前端
- `pnpm start:system`：启动 `system-service`
- `pnpm start:middleware`：启动 `middleware-service`
- `pnpm lint`：执行根级 `oxlint` 包装脚本
- `pnpm test`：并行执行 `apps/*` 与 `web/*` 子项目 Vitest 测试，并汇总覆盖率到根 `coverage/` 目录
- `pnpm tsgo`：通过 `tsgo` 执行根级 TypeScript 校验包装脚本

## 3. 自动扫描注册说明

当前启动链路默认依赖 `../NestCloud-Sdk/src/register/index.ts` 中的自动扫描注册机制，默认扫描模式为 `dist/**/*.js`。

这意味着：

- 标准启动链路默认依赖编译产物参与装配
- 如需调整扫描范围，应优先通过 `ConfigKeys.Pattern` 或统一启动链路调整
- 不应因为局部维护便利而回退到各服务手工注册 controller / provider 的模式

## 4. 校验脚本

- `scripts/run-oxlint.mjs`：统一执行根级 `oxlint`
- `scripts/run-tests.mjs`：并行执行 `apps/*` 与 `web/*` 子项目测试，收集各子项目覆盖率并生成 `coverage/summary.md`
- `scripts/run-tsgo.mjs`：先构建本工作区各项目并调用根工作区 `tsgo --noEmit -p <tsconfig>` 逐个校验各服务
- TypeScript 路径别名通过 `tsconfig` 的 `paths` 维护，不再依赖 `baseUrl`

提交前至少应关注：

- lint 是否通过
- test 是否通过
- tsgo 是否通过
- 暂存区内容是否与工作区一致

## 5. 配置约束

开发过程中需要遵循以下规则：

- 配置统一通过 `getConfig` 和 `ConfigKey` 获取
- 日志统一使用 logger，不使用 `console`
- 可复用静态值应提取为常量
- 无状态通用逻辑优先收敛到 `utils`
- 查询接口需要传递数组型条件时，优先使用 query 参数 + form 校验，支持重复 query 参数或显式约定的逗号分隔格式

## 6. 文档协同要求

开发中涉及以下变更时，需要同步更新文档：

- 架构边界或模块职责变化：更新 `/docs/project`
- 共享能力变化：更新 `../NestCloud-Sdk/docs/<能力>/`
- 服务模块变化：更新 `apps/<service>/docs/<模块>/`
- 可复用失败经验：更新 `/docs/experience/`

补充约束：`docs/plan` 只记录方案过程与执行状态；一旦实现落地，接口、交互、缓存、共享能力等最终事实必须同步回正式模块文档，不能只停留在计划文档中。
