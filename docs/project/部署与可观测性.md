# 部署与可观测性

## 1. 部署角色

SolaCloud 与同级仓库配合运行。

- 基础设施层：`NestCloud`
- 入口层：`gateway-service`
- 业务服务层：`system-service`、`middleware-service`、`rag-service`
- 共享能力层：`NestCloud-Sdk`（构建后被其他服务依赖）

部署时需要优先保证基础设施服务可用，再启动依赖它们的业务服务。

## 2. 配置与启动依赖

当前活动数据库服务统一使用 PostgreSQL；本地 `.env` 默认通过 `DbDriver=postgres` 与 `DbPort=5432` 接入。

新建业务库后先执行 `CREATE EXTENSION IF NOT EXISTS vector`，再依次执行 `sql/init.sql`、`sql/init_data.sql` 和 [SDK 幂等表脚本](../../../NestCloud/sql/sdk/add-rpc-idempotency-record.sql)。在另一数据库执行同级 NestCloud 仓库的 `sql/init.sql`，初始化配置中心表。

三个后端各自从工作目录的 `.env` 读取配置，可从同目录的 `.env.example` 起步。示例使用 127.0.0.1 上的 PostgreSQL 5432 和 Redis 6379。会话使用 Redis DB 2，队列使用 DB 3。会话、队列和上传状态均带独立前缀。应用为本地开发使用的上传文件和工作区保存在仓库根目录的 `.local-data/`。

若 NestCloud 启用了控制面鉴权，在三个后端的 `.env` 或进程环境变量中设置相同的 `ControlPlaneToken`，并配置本地 `RegistryUrl`。使用构建后的同级 SDK，注册和远程配置请求会自动携带凭证。Token 和鉴权时的目标地址由部署配置确定。

三个业务服务均从本地或远程配置、部署环境变量读取非空的 `SessionSecret`。共享登录态的实例须使用相同的密钥，并配置同一个 `SessionRedisUrl`、前缀和过期时间。省略 Redis 地址时，各实例使用进程内会话。

### 配置中心

业务服务若启用配置中心，会通过 `NestCloud-Sdk` 在启动阶段访问远程配置拉取接口。

### 注册中心

三个业务服务在 `NodeEnv=production` 时会向 `RegistryUrl` 注册实例并发送心跳。需要通过 HTTPS 网关调用时，在被调用服务设置 `ServiceBaseUrl=https://middleware.example.com/api`，并确认调用方可以解析该域名、信任其证书。未指定完整地址时，新客户端广播 `ServiceHost`、`Port` 和 `GlobalPrefix` 组成的 HTTP 地址。

升级时先部署注册中心和消费端，再启用新的 HTTPS 广播地址。老消费端只识别 `host`、`port`，同一服务逐步升级期间应保持该地址可达。要恢复原有 HTTP 调用，移除 `ServiceBaseUrl` 并重启提供方完成重新注册，消费端下次同步时使用新的实例地址。

这意味着：

- `NestCloud` 不可用时，依赖远程配置或注册中心的服务会受影响
- 需要保留本地配置作为降级路径

### 网关部署

管理前端部署为静态站点。构建时将 `VITE_GATEWAY_ORIGIN` 设置为浏览器可访问的 HTTPS 网关 origin，例如 `https://api.example.com`。网关的 `GatewayAllowedOrigins` 设置为实际的前端 origin 列表，例如 `https://admin.example.com`。将两者部署在同一站点的 HTTPS 子域下，以兼容默认 `SameSite=Lax` 会话 Cookie。健康检查使用网关的 `/health/ready`。生产将 `GatewayUpstreamMode` 设置为 `registry` 并提供私网 `RegistryUrl`。上游注册的 `ServiceHost` 和 `Port` 需从网关可达。

部署入口关闭聊天 SSE 的响应缓冲。上传请求同样使用流式转发，入口的请求体和空闲超时应匹配网关配置。让独立文件域名的 `/public/uploads/` 访问 middleware-service，并将对应外部 URL 写入 `UploadPublicBaseUrl`。使用本地磁盘时，middleware-service 保持单实例。

升级 middleware-service 到 BullMQ 6 时，先停止使用同一队列前缀的旧进程。新版启动时沿用已有清理任务的调度键，通过 Job Scheduler 更新调度，再启动 Worker。

先部署支持前端来源的网关，再发布引用该网关地址的前端产物。发布时观察网关的 5xx、CORS 预检和 SSE 首包。需要回滚时可重新发布上一版前端及其配套入口配置。[网关实现逻辑](../../apps/gateway-service/docs/网关/实现逻辑.md)

## 3. 注册中心存储模式

`../NestCloud/src/registry-center/registry.service.ts` 当前支持两种模式：

- Redis 模式：配置了 `RegistryRedisUrl` 时启用
- 内存模式：未配置 Redis 时回落到内存存储

部署文档与运维手册应明确当前环境使用的模式。

## 4. 日志

公共日志实现位于 `../NestCloud-Sdk/src/logger/logger.service.ts`。

当前特征：

- 基于 winston
- 控制台日志级别通过配置解析
- 默认非生产环境开启控制台输出
- 捕获未处理 Promise 异常与未捕获异常

## 5. 可观测性

公共 HTTP 入口、服务间调用和队列 Worker 使用 OpenTelemetry span，按 W3C 规则传播链路上下文。使用响应头 `x-trace-id` 搜索调用双方的日志；客户端每次重试使用独立 span。进程可接入已配置的 tracer provider，默认部署无需运行外部采集器。[链路传递与重试](../../../NestCloud-Sdk/docs/http/链路传递与重试.md)

启用管理后台集中日志查询时，由 Alloy 将各实例日志送入私网 Loki，各 system-service 实例使用同一 Loki 和日志 job。已有数据库应用菜单权限补丁后，部署 system-service、网关和前端。管理员可从「运行与审计 → 集中日志查询」使用响应头的 traceId 查找日志。[集中日志查询配置](../../apps/system-service/docs/trace-log/实现逻辑.md)

启用文件描述写重试前，在所有 `middleware-service` 接收实例共用的业务数据库执行 `../NestCloud/sql/sdk/add-rpc-idempotency-record.sql`（从 SolaCloud 根目录运行）。NestCloud 仓库维护这份 SQL。它创建的 `rpc_idempotency_record` 与文件记录位于同一个数据库，确保响应和文件更新能在同一事务中提交。新建业务库和已有业务库均需这一步。随后升级全部接收实例，最后开启调用方写重试。[写请求发布与回退](../../../NestCloud-Sdk/docs/http/写请求幂等.md)

运行中间件 PostgreSQL 集成测试时，将 `NEST_CLOUD_TEST_POSTGRES_URL` 设为独立测试库的连接串，在 SolaCloud 根目录执行以下命令。测试会创建并清理随机 schema，默认读取同级 NestCloud 仓库的同一份 SQL。若两个仓库不在同一父目录，将 `NEST_CLOUD_TEST_RPC_SCHEMA_FILE` 设为该 SQL 的绝对路径。

```sh
pnpm --filter middleware-service exec vitest run --config ../../scripts/vitest.backend.e2e.config.ts src/__tests__/file-retry.e2e-spec.ts
```

## 6. 运维文档同步场景

以下变化发生时，必须同步更新本文档：

- 服务启动依赖顺序变化
- 注册中心存储策略变化
- 日志初始化策略变化
- 追踪链路接入方式变化
- 部署拓扑或回滚方式变化
